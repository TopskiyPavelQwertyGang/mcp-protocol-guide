# Архитектура MCP

Для первого знакомства достаточно держать в голове одну цепочку:

```text
USER
  ↓
HOST
  ↓
MCP CLIENT
  ↓
MCP SERVER
  ↓
TOOLS / RESOURCES / PROMPTS
```

## Host

**Host** — AI-приложение, с которым взаимодействует пользователь. Оно управляет общей логикой работы, моделью, подключениями и пользовательским контекстом.

## MCP Client

**MCP Client** поддерживает соединение с конкретным MCP Server и обменивается с ним сообщениями протокола.

Один Host может работать с несколькими MCP-серверами через отдельные клиентские соединения.

## MCP Server

**MCP Server** предоставляет ограниченный набор возможностей внешней системы через MCP.

Например, отдельные серверы могут предоставлять:

```text
filesystem server → файлы
CVE server        → данные об уязвимостях
database server   → разрешённые операции с БД
Git server        → данные репозитория
```

## Почему это полезно

Без общего протокола каждая пара «AI-приложение ↔ интеграция» требует собственного способа подключения.

MCP вводит общий контракт, благодаря которому клиент может обнаруживать доступные возможности сервера и работать с ними стандартизированным образом.

## Где находится граница доверия

Важно не путать **стандарт взаимодействия** и **контроль доступа**.

```text
AI / Host
    │
    │ MCP
    ▼
┌──────────────────────┐
│      MCP Server      │
│                      │
│ auth / validation    │
│ permissions          │
│ allowlist            │
│ business rules       │
└──────────┬───────────┘
           ▼
      External system
```

Если инструмент опасен, одного описания вроде «используй осторожно» недостаточно. Сервер и внешняя система должны самостоятельно обеспечивать реальные ограничения.

Следующий репозиторий learning path — `mcp-secure-agents` — посвящён именно этой границе.
